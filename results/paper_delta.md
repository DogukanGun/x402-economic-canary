## 3. Expected USDC saved per routed call

The published run evaluated one routing policy: **pay with probability p-hat**.
Section 4 motivates a different one — "a well-calibrated probability translates
directly into correct expected-value routing" — which is the threshold rule
**pay iff p-hat x value > price**. The distinction is not cosmetic: at value
$0.02 and price $0.001, a provider delivering 65% of the time is worth paying
every single time, yet the soft policy skips it a third of the time and forgoes
more value than the stalls it avoids.

| policy | paper | published cfg | paper-spec cfg |
|---|---|---|---|
| soft (pay w.p. p-hat) | 0.000278 | 0.0002782 | -0.001568 |
| ev (pay iff p*v > c) | _no generating code_ | — | 9.961e-05 |

Under the paper-spec corpus the soft policy is **net negative** and the
expected-value policy is **net positive with a CI excluding zero**. The
paper's qualitative claim — routing on canary verdicts beats always-pay —
holds, but only under the decision rule Section 4 describes, not the one the
code evaluated. In the published run the two agree, because oracle-mode
probabilities are already near 0 or 1 and the soft policy rarely abstains.

## 4. Oracle mode vs forecast mode

The published predictor is fed the **current probe's own** post-payment
observables: `artifact_valid`, `schema_valid`, `http_status`, its own gap
(`repro/canary.py:16-28`). That grades a call which already happened. The
abstract sells something else — "an honest probability that your **next** paid
call will deliver" — and Section 3 defines the features as history
(`z_{e,t}` over delivery rate, p95 latency, gap history).

Both are implemented and both are reported:

| framing | features | target | stalled P | stalled R | PR-AUC | Brier |
|---|---|---|---|---|---|---|
| oracle | same-probe observables | this call | 1.000 | 1.000 | 0.998 | 0.0000 |
| forecast | causal endpoint history | next call | 0.944 | 0.723 | 0.898 | 0.1098 |

Oracle mode reaches a perfect 1.000 on the paper-spec corpus. That is not a
better detector — it is close to a tautology: you cannot consult it before
paying, because obtaining its features *is* the paid call. Forecast mode is
strictly harder and is the only one of the two that can inform routing.

Forecast mode misses two of the paper's Table 2 acceptance targets:
* `recall>=0.85`
* `brier<=0.10`

These are reported as computed. Nothing was tuned to close them.

## 5. Table 1 — component ablation (previously unbacked)

| configuration | paper P / R / PR-AUC | oracle cfg | forecast cfg |
|---|---|---|---|
| full canary | 0.994 / 0.983 / 0.861 | 1.000 / 1.000 / 0.998 | 0.944 / 0.723 / 0.898 |
| - delivery rate | 0.976 / 0.951 / 0.821 | 1.000 / 1.000 / 0.992 | 0.938 / 0.727 / 0.899 |
| - p95 latency | 0.989 / 0.972 / 0.847 | 1.000 / 1.000 / 0.999 | 0.942 / 0.728 / 0.899 |
| - settlement-to-response gap | 0.943 / 0.897 / 0.762 | 0.996 / 0.996 / 0.981 | 0.931 / 0.734 / 0.899 |
| - CUSUM (threshold only) | 0.968 / 0.929 / 0.861 | 0.978 / 1.000 / 0.998 | 0.932 / 0.723 / 0.898 |

The paper's qualitative claim — that removing the settlement-to-response gap
hurts most — **reproduces in oracle mode** (it is the only removal that moves
precision or recall) but the magnitude does not: the paper reports PR-AUC
falling to 0.762, and the computed drop is far smaller. In forecast mode the
gap enters only as a rolling mean and removing it barely matters.

The caption's invariant — PR-AUC unchanged when only CUSUM is removed —
holds in both framings.
